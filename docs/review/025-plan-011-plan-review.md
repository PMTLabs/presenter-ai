# r011-plan — independent plan review

Read-only review of `docs/plan/011-press-to-ask.md` against the stacked plan-010 implementation. No tests/builds, repository edits, or secret-file reads. The confirmed requirement, including **Extend** and the disabled transcriber, is taken as given. Locations below use repository-relative paths and line numbers. Classification: **A** = a fix applied to some sites but missed others; **B** = an oracle identifies its subject with too few fields; **C** = a claim unsupported by current code; **D** = a new design gap.

## Findings

### C1 — Socket frame order is not guaranteed to be presenter command order
**Severity:** blocker. **Plan:** §4.4 handoff table, line 513; T5, lines 735–739; chain map, lines 797–800.

**Unsupported claim:** “the socket's frame order is the loop order (frames sent before `ask_done` are recorded).” The bridge consumes socket frames sequentially but **does not await** either audio or text commands: `PresenterBridge.cs:355-388,444-460,519-538`. `Presenter.cs:357-374` writes to a bounded, waiting channel (`:52-58`) asynchronously; on saturation a write is pending while the bridge accepts the next socket frame. The receive-loop ordering alone therefore does not establish the claimed write/consumption order. A queued `ask_done` can overtake pending binary-frame writes, or `ask_start` can overtake late queued audio. Even if a particular channel implementation normally queues writers FIFO, that property is neither contracted nor tested here; cancellation of a pending write makes the boundary still less reliable.

**Fix:** Define a serial bridge→presenter admission path for *binary and ask control frames together*, with bounded/cancellable admission and disconnect cleanup, or prove and pin a precise FIFO guarantee for pending writes; do not block the presenter loop on the bridge. Gate a test with the 256-place event queue full: send distinct PCM frames before `ask_done`, then more after it; assert exactly the pre-done bytes reach the recorder, in order, with neither loss nor post-done inclusion. Also exercise start/mic order and disconnect during a pending write. Update the handoff table accordingly.

### A1 — Upstream-silence gate covers newly arriving calls, but not already running work or all unmute paths
**Severity:** blocker. **Plan:** §4.1 gating/commands, lines 264–291; §4.4 parallel paths, lines 529–532; T4, lines 679–688.

**Sites covered:** `OnAudio`, `OnToolCall`, `OnDelegation`, tool-originated `Next/Prev/Goto/Pause/Resume/ConfirmEnd`, and new mic frames. **Sites missed:**

* Authenticated `unmute` remains callable while asking (`PresenterBridge.cs:456-459` → `Presenter.cs:2170-2179`), because only *Mute* is assigned an ask policy. It can unmute the upstream before Ask done. The `_muted` flag is not the ask mute; `ReconnectAsync` re-mutes only for `_muted` (`Presenter.cs:2083-2086`).
* A tool invocation that began **before** Ask completes while Paused: `OnToolInvocationCompleted` accepts Presenting **or Paused**, submits its result, then calls `TryContinueResponses` (`Presenter.cs:1699-1733`). `OnDelegatedResponse` also calls `TryContinueResponses` and re-arms a question hold without a state/ask check (`:1472-1518`); `OnApprovedToolCompleted` can append commentary/thinking for a pre-Ask confirmation (`:1783-1801`). These can drive another upstream response during recording even though *new* calls are refused. Mute is an **input** command (`LiveSession.cs:219-226`), not an output/delegation cancellation command. The browser drops voiced audio but the server can still perform and complete tool work.
* `TrainOnTurnCore` is expressly allowed during Ask and `EnqueueEdit` appends `ScriptEditPendingInstruction` even when Paused (`Presenter.Training.cs:254-281,363-381`). Reconciliation appends `ScriptEditFailedInstruction` on failure while Paused (`:461-480`). An instruction append can elicit upstream speech during Ask, contrary to “Nothing is spoken … until Ask done”; it can also compete with the subsequent question.

**Fix:** Specify the policy for explicit `unmute` (refuse without changing upstream mute), outstanding tool/delegation completions and `response.create`, and trainer instruction appends while `_ask` is set. Make pre-Ask work inert/deferred where feasible, or explicitly bound the unavoidable upstream side effect and state the resulting acceptance limitation; gate tests with completion **after** Ask starts. Defer training's model-facing acknowledgements/failure instructions until the ask exchange finishes while still allowing the edit itself. Test `unmute` over `/ws`, pre-existing tool completion and edit success/failure during listening, not only a new `next_slide` call.

### D1 — Pause/ask transition leaves a live speech source before Ask done
**Severity:** major. **Plan:** §4.1 Ask start, lines 184–193, and §4.4 sequence (a), lines 405–414; T4 AC1, lines 679–687.

`PauseCore` appends a natural-language pause instruction (`Presenter.cs:2016-2033`, `PromptBuilder.cs:149-150`); the proposed sequence sends it **after** input mute. This controls narration but cannot cancel existing queued backend generation. The gate will suppress browser output *once handled*, yet neither the plan nor T1 tests what upstream does with a pending delegation/response or pause-instruction-generated audio during a real mid-sentence ask: T1 deliberately waits until narration has already been quiet for three seconds (plan lines 600–605). A 3-second-quiet probe does not prove the stated immediate mid-narration behaviour.

**Fix:** Add a distinct live mid-narration interruption observation to T1/T8: start while audio and a tool round are active, assert flush latency, absence of emitted playback while listening, and what happens to pending upstream output when Ask is sent. Clarify that the invariant is **no audible or newly acted-on output**, not “upstream cannot produce audio,” unless a real upstream control is established. This also bounds the acknowledged R3 rather than merely observing a successful quiet-session burst.

### D2 — Ask exchange does not isolate burst transcripts or guarantee an answer before resuming
**Severity:** blocker. **Plan:** §4.1 Ask done/exchange, lines 219–247; §5 error recovery, line 555; T4 AC2–AC3, lines 689–705.

The plan clears `_ask` and sets `_askAwaitingAnswer` until the **first voiced** output. It then stops shielding transcript deltas from `AppendUtterance`. But the existing transcript handler adds every user delta to the assembler (`Presenter.cs:1095-1151`), and `OpenOrExtendQuestionHold` resets `_answerVoiced`, restarts the 15-second timer, and clears silence/wrap-up timers *on every delta* (`:2459-2473`). A delayed transcript fragment of the same burst **after** filler or the first voiced answer can be parsed as a voice command (e.g. “next slide”), reset Answering, and release the hold. Conversely, a slow 120-second retained burst may take longer than the existing **15-second question-hold** window before a real answer: `OnQuestionHoldElapsed` calls `ResumeAfterQuestion` when none has started (`:2324-2331`), so its new `!_heardOutput` branch can resume/nudge the slide **before** the promised answer. First voiced audio could also be an old pre-Ask response (R3), not the ask's answer. A null timestamp alone fixes none of these.

**Fix:** Define an explicit ask-exchange phase distinguishing *the burst's late transcript* from new post-answer user speech, without relying on an unverified stream timestamp; say what observable boundary ends it. Give Ask a bounded answer-start budget justified by T1's **longest allowed kept audio**, instead of releasing the generic 15-second hold into narration. Preserve the ability to hear a real “yes/no” during check-in. Gate tests with transcript arriving after the first voiced answer, an old-answer frame, and answer latency straddling 15 seconds; assert no navigation, exactly one answer/check-in, and no premature slide narration.

### A2 — Trainer replay is deferred only while Paused, not throughout the ask exchange
**Severity:** blocker. **Plan:** §4.1 exchange/reconcile, lines 243–247, 274, 284; §5 edge cases, line 556; T4 trainer, lines 718–722.

**Covered site:** a commit *while still listening* reaches `ReconcileWithHead` with state Paused and sets `_replayOnResume` (`Presenter.Training.cs:489-502`), for which the plan adds a branch in `ResumeAfterQuestion`. **Missed sites:** Ask done sets state Presenting without consuming that flag (plan lines 219–228), while the same edit can finish **during** the subsequent answer/check-in. In Presenting, `ReconcileWithHead` calls `ReplayCurrentSlide` immediately (`Presenter.Training.cs:489-496,532-552`), which flushes playback and appends narration over the answer. An edit that failed while Paused appends the failure instruction immediately (`:461-480`); an unsettled hold may block the later resume. The proposed `ResumeAfterQuestion` branch cannot undo an earlier replay, and `ClearQuestionHold` clearing ask-exchange flags (`Presenter.cs:2475-2487`) risks losing the only phase gate before it is consumed.

**Fix:** Teach reconciliation, failure/pending instruction production and hold release about the **entire** ask exchange, not merely `_ask` or Paused. Defer replay/notice until after answer and check-in (specify what happens on “no,” timeout, End and navigation), then consume `_replayOnResume` exactly once. Test commits on both sides of Ask done and during voiced answer and carry-on, with a pending hold and failed edit; assert no stale slide instruction/flush interrupts the answer and exactly one eventual replay.

### D3 — Successful send is inferred from queue admission; mid-burst failure has no recovery boundary
**Severity:** major. **Plan:** §4.1 Ask done, lines 219–228; §5 recovery, line 555; T4/T5 send-order tests, lines 689–692, 735–739.

`LiveSession.SendAudio` returns success when it **enqueues** an `AudioFrame`, not when the socket sends it (`LiveSession.cs:229-243,306-330,729-731`). Its send loop can drop already accepted frames when closing/not open (`:311-330`); send errors close asynchronously. The plan says “If the session is gone or refuses an append, the ask is cancelled with `send_failed`,” but it also clears `_ask` first and may already have enqueued `unmute` and the first N chunks; there is no rollback, no acknowledgment for a partial question, and no guarantee that unmute is undone. `PumpFrame`s can also interleave with the burst in the same queue (`:409-444`), so an exact uninterrupted wire-burst assertion cannot just inspect producer-side `Sent` entries.

**Fix:** Define failure/close handling *before*, *during*, and *after* enqueue: when a partial burst may have reached upstream, fail/close that upstream session rather than promise “ask again” on the same session; no false `off{sent}` after a detected failure. If the implementation cannot know wire delivery, explicitly say so and test a gated send-loop failure at chunk N plus `session.closed`, in addition to `FakeSession.SendAudio=false`. In the wire test account for pump-generated silence separately and verify the actual ordered client chunks, not just queue calls.

### B1 — T1's pass oracle can approve a model that answered only the second half
**Severity:** blocker. **Plan:** §6 T1 pass rules, lines 600–629; AC2, lines 60–63.

The pass rule identifies the user question by **part-2 keywords only** and the answer by addressing **part 2**. A wrong implementation that discards part 1, keeps/transcribes part 2, answers “how much did it cost?” once, stays silent before the last chunk and makes no second response passes (i)–(vi); it does **not** answer “what did the programme change … and how much …?” Similarly, a transcript with part 1 in one completed turn and part 2 in a second completed turn, without intervening assistant audio, passes the stated transcript checks. The raw control is evidence, not an oracle.

**Fix:** For **each** en/vi run require one identified user question containing distinct part-1 **and** part-2 facts in order (or independently demonstrate both parts arrived in one model turn), and one answer containing independently scorable facts from **both** halves, with no intermediate response/delegation. Include at least one run near the retained-audio cap and measure send duration and answer-start against the 15-second hold; mark any split, partial answer or wrong turn as failure, not variant-B eligibility. Record actual criteria and usage seconds without storing audio or secrets. A wrong part-1-discarding implementation must fail the oracle.

### A3 — Control gating and toast policy do not agree for muted Ask
**Severity:** major. **Plan:** §4.1 P-4 and Web, lines 79–80, 328–339; §4.3 toasts, lines 372–381; T6 and T8, lines 758–767, 859–860.

**Covered:** the server returns `refused_muted` with a toast mapping. **Missed:** the planned Ask button is **disabled** when muted and the planned `A` handler calls `askStart` only when unmuted; it specifies no local warning. Consequently the T8 “Mute, press A → toast ‘Unmute …’” cannot happen through this UI. `MuteCore` really sets `_muted` and publishes the snapshot (`Presenter.cs:2158-2168`), on which the key handler uses `snapshot.muted` (`Present.tsx:333-353`). An injected `refused_muted` event in a toast unit test would not prove the key/button hop.

**Fix:** Either let `A` while muted show the same **local** warning (button may remain disabled) and test the real action, or change the runbook/AC for the disabled UI to expect the button's hint and test the refusal only through a raw `/ws` call. Keep server-side refusal regardless of UI policy. Include `refused_not_live`, `send_failed` and cancellation toasts in action-level tests, not merely synthetic store messages.

### D4 — Phrase completion uses an unrelated clock as its utterance delimiter
**Severity:** major. **Plan:** §4.1 transcriber matcher, lines 303–319; T4 AC5, lines 721–726.

`quietMs` is measured from **mic PCM energy** (`lastVoicedAt` in the proposed recorder), whereas `TextChanged` is a cumulative transcript arriving on an arbitrary thread. The existing 700-ms utterance assembler instead starts its timer **when a transcript delta arrives** (`Presenter.cs:1131-1151`). With a delayed transcriber, a delta ending in “I'm done” can arrive >700 ms after the audio and match **immediately**, without knowing whether more text for that same utterance is pending; a late reordered/duplicate older cumulative text can also replace the most recent text even though the plan calls it “idempotent” (§4.4, line 515). The disabled production default does not repair the required test-plug-in behaviour.

**Fix:** Give transcriber updates a monotonic revision or an explicit utterance-final marker; use an update-time debounce/finalization or a documented audio/transcript watermark to decide end-of-utterance. Ignore stale revisions on the presenter loop, not merely stale ask ids. Test delayed, reversed and duplicate updates, phrase embedded before trailing words, and an actual >700-ms finalized suffix; retain the disabled registration and no text persistence.

### C2 — The plan promises no persisted ask transcript, but the existing recorder persists it
**Severity:** blocker. **Plan:** §2 constraints, lines 47–53; §5 data consistency, line 551; T7 wiring audit, lines 770–779.

**Unsupported claim:** “No audio or transcript is persisted.” The same plan later says “the upstream transcript of the burst is recorded by `SessionRecorder` like any spoken question.” That is exactly what current code does: `Presenter.OnTranscript` broadcasts **all** transcript deltas (`Presenter.cs:1095-1107`); `SessionRecorder` subscribes (`SessionRecorder.cs:80-84`), buffers them (`:171-175,311-332`), and persists turns. The disabled `IAskTranscriber` only stops *that plug-in's* output; it does not disable upstream transcription after Ask done. The confirmed no-persistence constraint is not met by the proposed design.

**Fix:** Specify the privacy boundary explicitly: tag ask-burst transcript events before the recorder, and ensure neither raw ask audio nor the ask transcript (including delayed upstream deltas and the stripped phrase) reaches persisted session turns, while preserving the live transcript needed by the UI/check-in. If the intention was instead only “no *additional* ask-specific transcript persistence,” reconcile §2 with §5 explicitly with the owner, rather than silently weakening the confirmed constraint. Test a recorded real-DI talk with an ask-burst user transcript and ordinary pre/post-ask turns: the latter persist, ask text does not, even if burst transcript deltas arrive late.

### D5 — Pause-grace suspension is stopped only after a fallible/awaited start sequence
**Severity:** major. **Plan:** §4.1 Ask start, lines 184–193; §4.4 sequences (a),(b), lines 403–452; T4 guard tests, lines 705–713.

Ask from suspended first awaits `ReconnectAsync` (`Presenter.cs:2066-2091`), which calls `OnTrainingSessionReady(reconnected:true)` before the proposed `_ask` is set; reconciliation can mutate held narration during that await/return (`Presenter.Training.cs:160-169,415-502`). In the live Paused path the existing pause-grace timer is still armed until *after* mute, reset/clear and `PauseCore` have run (proposed order); a queued `GuardElapsed` is checked by generation in the presenter loop (`Presenter.cs:490-493`) and `TalkGuard.Due` can already report Pause (`TalkGuard.cs:68-96`). On ordinary, non-blocked execution it will likely be suppressed by rescheduling, but the plan's unconditional “upstream is never suspended mid-ask” has not specified this boundary or failure handling for `Mute()`/`Begin()`.

**Fix:** Treat the Ask transition as atomic on the loop once reconnect has succeeded, stop pause grace before any fallible ask initialization, check current session/state after reconnect, and define rollback (grace rearmed, input unmuted or talk closed) for failed mute/transcriber begin. Test Ask enqueued immediately before grace expiry, timer event already queued, reconnect failure, and transcriber Begin throwing; assert no stranded Paused session with upstream muted. Do not mutate ask state off-loop to achieve it.

## Verified design anchors and remaining audit

* The stated current-state anchors are broadly accurate: loop commands and producer queue (`Presenter.cs:225-250,357-405,428-508`), mute/unmute/send FIFO **admission** (`LiveSession.cs:204-243,306-330`), 15-second hold and null-end timestamp comparison (`Presenter.cs:2459-2496`), pause/guard/reconnect (`:2016-2033,2066-2108`; `TalkGuard.cs:50-76`), plan-010 hold/replay (`Presenter.Training.cs:415-573`), and bridge disconnect ownership (`PresenterBridge.cs:204-232`). Do not confuse FIFO *admission* with guaranteed socket delivery or with bridge receive ordering (C1/D3).
* A separate loop-only `_ask` is justified by the existing interaction resets (`Presenter.cs:676,1122,1232,1269,1358,1380,1756,1766,2025,2115,2133,2202,2268,2484,2502`). Stopping pause grace is available (`TalkGuard.cs:76-80`); max length is independent (`:85-94`). From Paused, answer routing through Presenting avoids the 1.5-second permit (`Presenter.cs:1005-1010,1296-1312`). The chosen 120-second **retained**-audio cap and Extend policy are confirmed design decisions, not objections.
* The handoff table is sound about *ownership* for mic frames, 1-second tick and transcriber callbacks **provided** all callbacks merely enqueue immutable payloads and disposal is observed, and about stale session identity for most upstream events (`Presenter.cs:911-921,997-1003,1095-1101`). Its ordering/idempotence claims are not sound for bridge frames (C1), old transcriber text (D4), ongoing upstream work (A1), or socket delivery (D3). `EndAsyncCore` and `OnClosed` are separate cleanup paths (`Presenter.cs:2185-2239,2259-2301`); T4 appropriately asks for both, but add End/max/disconnect while a command is waiting for queue admission and while a burst is only partly enqueued. An `off{ended}` sent before `closed` is meaningful only while the browser connection remains open; disconnect cleanup cannot deliver it to the disconnected socket.
* T2's disabled default and T3's suffix/longest/en/vi normalization tests are proportionate; `VoiceCommandMatcher` normalizes FormC and strips apostrophes (`VoiceCommandMatcher.cs:48-97`). Keep `IAskTranscription.Append` nonblocking, copy PCM before returning, and do not evaluate the lexicon from the disabled production implementation. T2's `StartupTests` proves API DI but not the asserted **both CLI modes** registration (plan T7 lines 772–777); add a concrete CLI construction oracle if that claim matters.
* Tasks have a sensible T1 gate, T2 contract dependency, then independent T3/T4/T6 lanes, T5 bridge after T4, T7 audit and T8 live run. T4's phrase tests explicitly land after T3. The AC matrix includes every AC, but the missing oracles above mean AC1–AC4 and AC5 are **not yet fully enforced** by the chain map. T1 must not be marked passing on partial answers; T4 must exercise old tool completion, training reconciliation during Answering, late burst transcript, unmute, and long-answer timeout; T5 must pin saturated-channel ordering and partial-send close; T6/T8 must agree on muted toast. These are targeted changes, not additional product scope.

## IS THIS PLAN READY TO IMPLEMENT?

**No. Blockers:** C1 (socket→loop boundary), A1 (incomplete upstream gate), D2 (exchange/transcript/15-second answer boundary), A2 (trainer replay during answer), B1 (T1 can approve a partial question), C2 (ask transcript persistence). **Improvements before approval:** D1, D3–D5 and A3; strengthen the named tests and handoff table as above. No confirmed requirement needs reopening. Do not run T2–T8 until T1's strengthened pass criteria are met.
