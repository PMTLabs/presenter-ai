## Findings

1. **D — High — A *pre-confirmation* yes can approve a tool requested later.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:574-596,614-640`; `src/PresenterAi.Application/Presenting/Presenter.cs:1624-1641`. The new logic checks whether `_pendingTool` exists **at utterance completion**, not whether its *first delta* arrived after the confirmation began. Reproduction on the loop: in `CheckIn`, a qualifying `yes` delta opens `exchange.UtteranceOpen` and arms its 700 ms assembler; before that timer fires, `OnToolCall(revise_script)` sets `_pendingTool`/`AwaitingConfirmQuestion`; when the already-open utterance completes, `CompleteExchangeUtterance` calls `ApproveToolConfirmation()`. The audience never said yes to this tool. The 1.5 s check on *opening* an utterance does not fix this ordering. **Fix:** record the confirmation-start generation/time and the purpose/start time of each utterance; reset or quarantine a check-in utterance when the confirmation starts, and accept only a fresh utterance whose first delta is after that start and after 1.5 s of transcript quiet. Add an event-interleaving oracle for delta → tool request → debounce (and the corresponding no/decline case), in addition to the existing tool → delta tests.

2. **D — High — A failed follow-up rollback can leave an `answering` exchange on a detached upstream.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:181-225,281-286,724-783,839-860`. For an Ask during `AwaitingAnswer`/`Answering`/`CheckIn`, if `_askTranscriber.Begin()` throws **and the rollback `SendUnmute` is refused**, `ResetUpstream()` detaches the session and pauses the talk, but `followUp` remains in the answer phase. `RefuseStart` then emits `off{unavailable}` followed by `answering` for this still-live exchange. No session can supply its answer or check-in; its old answer timer may emit another `off{continued}`/resume into a null session. Ordinary ask-start rollback was handled, but the newly allowed in-place follow-up is not. **Fix:** on failed rollback while a follow-up exists, terminate that exchange exactly once (`send_failed`/unavailable Stay as appropriate), preserving deferred notices for reconnect and replay due; do not re-announce answering on a detached session. Test failed Mute, failed Begin, and refused rollback Unmute in each answer phase, asserting state, off count, usage and recovery after reconnect.

3. **A — Medium — Follow-up refusal recovery covers fallible steps but misses the earlier refusal branches.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:164-181,187-198,206-225,281-286`. `RefuseStart(followUp, reason)` restores `answering` after a refused Mute or Begin. The earlier `_muted` and missing-session/reconnect-failure branches still call only `EmitAskOff(null, "refused_…")`, even when an answer exchange is active. A user Mute during Answering is explicitly allowed and keeps the exchange running (P-16). A subsequent socket `ask_start` gets `off{refused_muted}`; the web store clears the Answering/Continue controls while the server remains in Answering/CheckIn, so the user loses Continue. **Fix:** compute the existing answer exchange before *all* refusal checks; reuse one refusal path which re-announces `answering` whenever the existing exchange survives (or ends it if the session is gone). Test `mute` → refused follow-up → unmute → Continue with frame sequence and exactly one eventual exchange off.

4. **B — Medium — The new follow-up oracle does not identify the carried-over exchange by its deferred/replay state.** `tests/PresenterAi.Application.Tests/Presenting/PresenterAskTests.cs:1698-1749`. Both follow-up tests use an exchange with **no deferred notices and no pending replay**. A wrong `BeginFollowUp` that clears `exchange.Deferred`, `ReplayDue` and `ReplayChanged` but keeps `NarrationHeard`/`FollowUps` still passes them, yet drops a trainer notice and resumes stale narration after an edit. The existing edit-replay tests exercise listening/answering/check-in **without a follow-up**. **Fix:** queue an edit notice and settle an applied edit during the first answer, then start two nested follow-up Asks and assert one final off, each notice exactly once, one replay of the correct version, and no premature resume; include End/max-length before the last follow-up completes and check no delayed replay/notices. This is a test gap, not a claim that current code clears those fields.
