## New findings

### D6 — Phase-only CheckIn cannot distinguish a late burst “yes” from a real answer to the check-in
**Severity:** blocker. **Plan:** emitter 15 `:269`, phase/end `:230-247`, T4 site-15 tests `:857-858`.

Until CheckIn, the plan treats user deltas as burst transcript; *at* CheckIn it interprets Yes/No/Resume/Pause as new live speech and explicitly claims “the phase boundary, not timestamps, separates late burst fragments.” But asynchronous `session.input_transcript.delta` has no burst/fresh provenance in `LiveSession` (`src/PresenterAi.Infrastructure/Live/LiveSession.cs:514-522`; presenter event stores only role/delta/start/end, `src/PresenterAi.Application/Presenting/Presenter.cs:2669`). An old burst delta “yes” arriving after Answering→CheckIn invokes the existing yes path (`Presenter.cs:1268-1276`) and prematurely resumes; an old “no” strands the talk. Site-15 tests inject late text **during Answering**, and independent *real* yes/no during CheckIn, so this interleaving passes all named tests. Conversely muting genuine user input until a verified burst boundary is established is not specified.

**Fix:** Define an observable burst-transcript completion/provenance barrier (or explicitly adopt and live-validate a bounded policy with stated limitations); do not assert phase alone distinguishes audio sources. Test delayed burst “yes/no” **after** CheckIn begins, followed by a real yes/no, with exactly one correct outcome; include delayed delta after follow-up timeout. T1 already records when the last burst delta arrives (`:748-753`), but that measurement alone is not a discriminator.

### D7 — A full admission queue prevents the bridge from even receiving an urgent `end` frame
**Severity:** blocker. **Plan:** admission `:422-434`, “End bypasses” `:424-425,640`, T5 `:929-933`.

The proposed receive loop **awaits a bounded queue write** when full (`:428-430`). It cannot call `HandleText` on a later `end` frame while stuck there. Thus “end bypasses admission” applies only *after* receipt; a user pressing End behind ≥256 queued PCM/control frames cannot trigger the existing off-loop `CancelConnect`/`EndWithReasonAsync` (`src/PresenterAi.Api/Realtime/PresenterBridge.cs:355-388,460,570-609`; `src/PresenterAi.Application/Presenting/Presenter.cs:252-275`). The admission pump itself awaits a stalled presenter command's completion, so neither drain nor End is guaranteed promptly; the heartbeat timeout is not a user-End guarantee. `End_bypasses_admission_and_a_queued_ask_done_is_ignored_afterwards` does not establish End is *received under full-queue backpressure*.

**Fix:** Specify an urgent-control lane/reader or nonblocking bounded receive staging that can accept `end` while PCM admission is backpressured, with clear ordering and memory bounds. Or explicitly refuse/close the connection at queue capacity so End is not advertised as immediately bypassing. Gate a test with pump blocked, admission **full**, an additional PCM write pending, then End on the same open socket; assert End cancels the old talk promptly without a burst, independently of heartbeat expiry. Keep disconnect/take-over cleanup distinct.

### A4 — Exhaustive 17-emitter gate misses a confirmation-decline instruction and a tool-call hold reset
**Severity:** major. **Plan:** “every one consults the exchange” `:247-271`; T4 site tests `:839-859`; single answer-budget replacement point `:273-277`.

**Covered:** direct trainer pending/failure/replay (sites 8–10), existing `OnDelegatedResponse`/`FinishBackendDelegation` re-arms (site 4), `OnDelegation` (site 7) and new `OnToolCall` refusal during Listening (site 2). **Missed:** `OnScriptEditDeclined` directly appends `ScriptEditDeclinedInstruction` (`src/PresenterAi.Application/Presenting/Presenter.Training.cs:360-363`) when `CancelToolConfirmation("not confirmed")` fires from `OnInteractionElapsed` (`Presenter.cs:1363-1368,1752-1759`); a `revise_script` call can be made during `AwaitingAnswer`/`Answering` because site 2 explicitly permits tools there, and its 8+10-second confirmation can time out during the exchange (`:1543-1604`). It then speaks/delegates a model-facing notice without `DeferUntilExchangeEnds`. Separately `OnToolCall` re-arms **the generic** question hold at `Presenter.cs:1565`, in addition to `OnDelegatedResponse` `:1486` and `FinishBackendDelegation` `:1519`; the proposed “single replacement point” for `ExtendAnswerWait` does not cover it. A slow tool can therefore outlast the answer-start budget and end the exchange while backend work is still pending. `OnUpstreamError` also reaches `FinishBackendDelegation` (`:1522-1540`): ensure this path consults the same gate instead of accepting an old unlabelled backend error as current.

**Fix:** Add the decline emitter and `OnToolCall`'s hold/budget transition to the inventory and T4 matrix. Route all `ArmQuestionHold` callers (including `OnToolCall` and `OpenOrExtendQuestionHold`, `Presenter.cs:2459-2473`) through a phase-aware answer-wait helper, with a finite maximum for outstanding tool work; defer decline notices, and test a tool call lasting past the original budget, timeout of a trainer confirmation during Answering, and the upstream-error finish path. A grep for `AppendInstructions` in `Presenter*.cs` must include `OnScriptEditDeclined`, not just `EnqueueEdit` and `ReconcileWithHead`.

### D8 — Refused-chunk reset has no defined async serialization with End/max length
**Severity:** major. **Plan:** “Ask done … one loop handler, no await” `:337-353`, send failure `:342-349`, handoff `:643`; T4 `:875-876`.

The claimed reset invokes the existing *suspend path*, but `SuspendUpstreamAsync` detaches `_session`, **awaits** `session.CloseAsync` and session disposal before marking usage/status/snapshot (`src/PresenterAi.Application/Presenting/Presenter.cs:2035-2052`). `ILiveSession.CloseAsync` is asynchronous (`src/PresenterAi.Application/Presenting/ILiveSession.cs:38-48`); its real implementation has a close timeout and the send loop can discard admitted frames while Closing (`src/PresenterAi.Infrastructure/Live/LiveSession.cs:245-276,306-330`). The plan specifies neither how the synchronous Sending handler waits for/reset-observes this operation nor how a concurrent End/max/disconnect is serialized with an off-loop close, or how its final usage is recorded exactly once when `SessionClosed` is ignored by identity (`Presenter.cs:448-454`). A fire-and-forget reset risks a stale completion setting `_suspended`/publishing Paused after End; awaiting it contradicts “no await” and delays the loop/End until CloseTimeout. The chunk-refusal test tests the final state, not End/max at this reset boundary.

**Fix:** Specify a dedicated serialized reset transition: detach and mark suspended on-loop, either await a bounded close on-loop **and explicitly accept/test the End latency**, or finish it off-loop and re-enter with a session/generation-guarded result for usage/disposal. Test close delayed past End/max/take-over after chunk N failed, late old `SessionClosed`, exactly-once usage and no stale Paused/suspended snapshot after closed.

### B2 — The admission test does not actually fill the claimed presenter event queue
**Severity:** minor. **Plan:** T5 `:925-931`; chain `:1004-1006`.

The test holds the presenter loop inside an awaited Ask-from-suspended reconnect, then sends 300 distinct frames; but **the single admission pump awaits the first presenter call's completion** before taking the next item (plan `:426-428`). Those 300 frames fill the **admission queue**, not the presenter's 256-place `_events` channel (`src/PresenterAi.Application/Presenting/Presenter.cs:52-58,357-374`). A wrong implementation that drains that admission queue by issuing all 300 `SendAudioAsync` calls **without awaiting their completions**, while the presenter channel is empty after reconnect, can pass the test on normally ordered channel writes; it has reintroduced the very unsynchronized boundary C1 sought to eliminate. `Admission_is_serial_and_backpressures_the_receive_loop` with a held fake is the test that must carry that oracle.

**Fix:** In that fake-presenter test require at most **one** presenter method call in flight, including audio, ask commands and disposal, and enforce socket-frame order using distinct payloads. Rename the real-presenter test to reflect admission-queue saturation; if presenter-event saturation is desired, arrange separate producer events while a command is in flight and assert their exact relationship rather than assuming the admission pump can fill it.
