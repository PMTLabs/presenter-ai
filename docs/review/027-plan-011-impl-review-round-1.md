# Implementation review — r011-impl-r1

Scope: `b39fde9..558b1db`; review only. No builds or tests were run.

## Findings

1. **D — High — An old unmute acknowledgement can release a *different* ask's burst early.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:327-335,608-610` and `src/PresenterAi.Infrastructure/Live/LiveSession.cs:567-568`. `UnmuteAcked` carries only the session, unlike the timeout's generation. After ask 1 times out at 2 s (or is cancelled during Sending), its late `session.input_audio.unmuted` can arrive while ask 2 is waiting on the *same session*. The handler treats it as ask 2's ack and sends ask 2's lead-in and recording before its own unmute is acknowledged. The sub-phase guard ensures at-most-once sending, not attribution to the right unmute. This also applies to an ack left by a cancelled ask. **Fix:** correlate acknowledgements to unmute requests (if the upstream echoes an event id), or retain/consume outstanding ack debt and make timeout/cancellation reset the upstream before reusing it when attribution cannot be guaranteed. Add a two-ask test: hold ack 1, cancel/time out ask 1, start/done ask 2, deliver ack 1, assert no ask-2 audio; deliver ack 2 and assert exactly one burst.

2. **A — High — Deferred trainer/limit notices are handled on ordinary exchange exits but lost on the send-failure reset.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:383-393,605-656,705-724`; missed exits for notices queued by `src/PresenterAi.Application/Presenting/Presenter.Training.cs:363-365,380-383,489-492` and `src/PresenterAi.Application/Presenting/Presenter.cs:2649-2652`. `FailSend` detaches `_session` in `ResetUpstream` *before* `EndExchange(Stay)` invokes the deferred closures. Those closures use `_session?.AppendInstructions`, so the list is cleared but no notice reaches either the old or the next session. Ordinary Stay/Resume paths emit them once. **Fix:** preserve semantic notices (not closures bound to the current nullable session) over the reset, then append once after reconnect; or explicitly make send failure a documented drop outcome with a visible failure/retry policy, rather than claiming Stay delivers them. Test each notice type with an append failure and reconnect.

3. **D — Medium — A confirmation requested during an ask answer cannot be approved or declined by voice.** `src/PresenterAi.Application/Presenting/Presenter.cs:1133-1140,1607-1639,1371-1417`; `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:472-489`. A `revise_script` tool call in AwaitingAnswer/Answering creates `AwaitingConfirmQuestion`/`AwaitingConfirmAnswer`, but *all* user transcript deltas before ask `CheckIn` take the UI-only exchange branch. Thus an actual spoken yes/no cannot reach `ApproveToolConfirmation`/`CancelToolConfirmation`; the 10 s timer declines it. `PresenterAskTests.cs:440-462` tests the timeout even though it sends `no`, not the desired confirmation behavior. **Fix:** give pending tool confirmation its own gated reply path during answer phases (while continuing to reject late question fragments, and without opening ordinary navigation commands); add affirmative and negative voice tests plus a delayed-question-delta negative test.

4. **D — Low — Transcriber is disposed twice.** `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:205-208,608-614,773-780`. Ask done and quiet-without-speech each call `Dispose`, then `EndExchange` calls it again. The port `IAskTranscription` does not require idempotent disposal. **Fix:** transfer ownership to one disposal site (once when listening finishes, or once at exchange end) and test with a disposable that throws on its second call.

5. **B — Medium — The socket-order/burst oracle ignores the very audio it claims to exclude.** `tests/PresenterAi.Api.Tests/BridgeAdmissionTests.cs:53-65` and `tests/PresenterAi.Api.Tests/BridgeAskTests.cs:391-400` (`IsBurstAppend`/`BurstAppends`). The admission test claims the burst contains *none* of the 55 post-`ask_done` mic frames, but identifies burst audio solely by encoded length `!=` a 960-byte frame. A wrong `SendAudioCore` that forwards those 55 frames during the unmute-ack wait passes its byte-for-byte `BurstAppends` comparison: they are all 960 bytes and disappear from the oracle. **Fix:** assert the actual upstream append stream and its ordering across unmute, ack, lead-in, burst and the post-done frames, using a held ack and distinct PCM payloads. Check no non-pump mic payload reaches upstream before ack; size alone is not a source identifier.

6. **D — Low (test race, not established production failure) — The observed G4 flake has a concrete timeout race.** `tests/PresenterAi.Api.Tests/BridgeAskTests.cs:17-18,45-56` versus `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:226-231,332-337`. The test holds the ack but lets the real 2 s acknowledgement timeout run. Its `WaitForAsync` under suite load plus `Task.Delay(300)` can cross that deadline *before* `UnmuteAckGate.TrySetResult()`: `BurstAppends` is then nonempty and the test fails without a regression. The failure assertion wasn't captured, so this is a plausible race, **not proof** that it caused the one recorded failure. **Fix:** use the API fake clock and hold it below 2 s until the pre-ack assertion, then release the gate; separately advance exactly 2 s in a timeout test. Capture the assertion on any recurrence. FakeLiveServer also sends ack/instruction audio on independent tasks (`FakeLiveServer.cs:354-363,442-466`), so avoid inferring wire order from task scheduling alone.

7. **C — Medium (coverage claim) — “one gated test per row” is not true as an *isolating* oracle.** `docs/plan/011-press-to-ask.md:246-247` says “T4 has one gated test per row”; `docs/research/010-plan-011-wiring-audit.md:136-164` records 11/23 `ExchangeAllows`/hold gates whose removal leaves suites green: sites **1, 3, 4, 5, 6, 7, 17, both site-11 gates, both site-12 gates**. They are layered defences; this does **not** establish 11 current behavioral defects. **Fix:** qualify the plan/test claim, retain the gates and mutation table, and where the invariant matters build scenarios that re-open the precondition *after* Ask (or use an explicit test seam). Do not weaken the existing parity tests.

8. **C — Low — Quiet-timeout diagram contradicts the implemented frame sequence.** `docs/plan/011-press-to-ask.md:696-699` says `off{quiet_sent} (toast), then (a)`, while §4.3 and `SendBurst` (`src/PresenterAi.Application/Presenting/Presenter.Asking.cs:379-383`) send `answering{quiet_sent}` followed later by one `off{continued|…}`. **Fix:** correct §4.4(c) to the actual sequence; the client already toasts on `answering`.

## Acceptance and gates

The T1 live-probe evidence (`docs/progress/002-work-log-phase0.md:654-723`) records a final PASS after the cap sweep; it is not a substitute for AC1–AC4's real browser/upstream T8 run. The recorder tests pin the 25 s *retained* cap and the byte-level burst; the ack, limit, End, max-length, reset-usage and Continue paths have meaningful unit coverage. P-16's deferred upstream Mute and pump behavior are tested. P-13's 1.5 s transcript quiet is tested on normal answer/check-in paths, but does not cover tool confirmations (finding 3); the known residual late-fragment risk remains documented. The reported second Ask during Answering producing `off{paused}` is confirmed at `Presenter.Asking.cs:99-120`; §4.1 actually prescribes `Stay` for a later-phase Ask, so this is an intentional but potentially surprising interruption policy, not an unplanned code defect. Product/UI clarification would help.  Web A/Enter/Space and frame handling appear aligned with §4.1/§4.3; no additional web blocker identified. The `ask_done` API only promises an accepted command/queued unmute, and an eventual send-loop failure can still close the talk, so its `true` result must not be interpreted as successful delivery.

## IS THIS BRANCH READY TO MERGE?

**No. Blockers:** correlate unmute acknowledgements (1), preserve or explicitly resolve deferred notices on reset (2), decide and fix voice confirmation during an answer (3). T8 live run remains a **separate known gate**.

**Improvements:** single disposal (4), strengthen the burst oracle (5), remove the wall-clock test race (6), correct coverage and diagram claims (7–8). No builds/tests were run for this review.
