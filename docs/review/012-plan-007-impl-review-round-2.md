## Findings (new or remaining)

### Blockers

- **D-01 · blocker · Timed-out tools can perform actions later, even in another run.** `src/PresenterAi.Application/Presenting/Presenter.cs:1153-1219,237-244`. `WaitAsync` times out the *wait*, not `InvokeAsync`; the underlying task may keep running. Example: a registered tool ignores cancellation, waits six seconds, then calls `IPresenter.NextAsync(CancellationToken.None)`. At five seconds the backend receives `{ok:false,"timed out"}` and continues, but at six seconds the tool still advances a slide. If End/Start happens in between, it advances the new talk. `PresenterToolTests.cs:295-315` releases its ignored-cancellation tool with a value only, never a presenter action. Suggested fix: run-specific capability/guard on commands issued by a tool (including commands enqueued before expiry), revoke it at deadline/navigation/End, and reject late side effects on the reader; cancellation alone cannot enforce this for arbitrary `ITool` implementations.

- **D-06 · blocker · Check-in No eventually resumes the narration.** `src/PresenterAi.Application/Presenting/Presenter.cs:733-748,827-833,866-871,1618-1626,1750-1765`. Speech "no" opens/extends a question hold and arms a 15 s timer *before* it is recognized. `keepHold` leaves that timer running. With no further speech, after 15 s `OnQuestionHoldElapsed` calls `ResumeAfterQuestion`, despite plan §3.7's "No → stay on the slide, hold kept for the next question." If any reply audio arrives, `_answerVoiced` and the 700 ms + follow-up timers can resume even earlier. The new test stops at 3 s. Fix: represent No as an explicit waiting-on-slide phase/hold, cancel unanswered/answer timers and do not interpret subsequent incidental output as a fresh answer; only a new question or explicit action leaves it. Test no further speech past 15 s and voiced output past the configured follow-up window.

- **A-01 · blocker · Output gating fixed Paused but missed Ending.** `src/PresenterAi.Application/Presenting/Presenter.cs:638-650,1430-1442,1507-1540`. Paused audio is gated; `OnAudio` forwards *every* frame in `Ending` because `state != Paused`. Press End or confirm End while the upstream continues to send old narration before `session.closed`/close timeout: queued `AudioReceived` events are delivered to the bridge and browser even after the End state was published. That violates instant stopping and can audibly continue the meeting. Fix: allow output only in Presenting or within the Paused speech permit, flush playback on entering Ending, and discard queued Ending audio; test delayed session close plus upstream audio and page flush.

### Improvements

- **D-02 · should-fix · The abandoned invocation retains a disposed arguments document and has no explicit late-fault observation.** `src/PresenterAi.Application/Presenting/Presenter.cs:1168-1219`. On a 5 s timeout the `using (doc)` disposes the `JsonDocument`, while the original `InvokeAsync(doc.RootElement, …)` can still be running. A tool that awaits an uncooperative I/O operation and then reads its `JsonElement` throws `ObjectDisposedException` after the timeout, with no continuation observing that late failure. Clone the `JsonElement` before invocation and attach a fault observer to the abandoned task; add a late **fault**, not just late-success, oracle. Also revoke tool-run permissions as D-01.

- **D-03 · should-fix · Navigation exemption is permanent until that call submits.** `src/PresenterAi.Application/Presenting/Presenter.cs:1229-1232,1243-1246,1423-1427`. A tool call `c1` navigates to slide 2 and then awaits a gate; a user presses Next to slide 3; on `c1` completion its id remains in `_navigatingCallIds`, so the tool result reports success about slide 2 rather than the required `{ok:false,"stale: the presentation moved on"}`. Remember the generation resulting from *that* call and accept it only if no subsequent navigation occurred; include a navigation-then-external-navigation ordering test. This matters especially if the backend makes its next tool decision from that outdated result.

- **D-04 · should-fix · A refused continue/output leaves a permanent, unreported barrier.** `src/PresenterAi.Application/Presenting/Presenter.cs:1239-1255`, `src/PresenterAi.Application/Presenting/ToolRoundTracker.cs:146-163`. In an open session where `ContinueResponses()` returns false transiently, no timer or later event retries the all-submitted round: the backend never receives `response.create` and the hold eventually expires. A refused `SubmitToolOutput()` similarly leaves the call pending after its only completion event has been consumed. The tests at `PresenterToolTests.cs:347-379` assert only non-advance and therefore pass an implementation that stays stuck forever. On refusal either retry safely with an explicit bounded policy or fail/close the delegation and report the transport error; test recovery or terminal handling, not merely that no progress occurred on the first refusal.

- **D-05 · should-fix · Invalid numbered-navigation reply loses the hold and can advance the deck after speaking.** `src/PresenterAi.Application/Presenting/Presenter.cs:816-825,693-725,1282-1320`, `src/PresenterAi.Application/Presenting/PromptBuilder.cs:160-161`. While Presenting on slide 1, user asks for slide 40. `ClearQuestionHold` precedes "There are slides 1 to N. Do not resume"; after the model voices that reply `OnAudio` sees no hold and arms ordinary advance, which moves to slide 2 on silence. The message says not to resume but the controller does. Keep an explicit response/hold phase or rearm only the interrupted slide's timer appropriately; test reply audio plus subsequent silence in managed and client mode.

- **B-01 · should-fix · Invalid-range test identifies an instruction, not a spoken reply.** `tests/PresenterAi.Application.Tests/Presenting/PresenterVoiceCommandTests.cs:54-72`. AC3 says an impossible target gets a *spoken* reply; a wrong presenter that calls `AppendInstructions` but discards every output frame passes this new test. Assert eligible model audio reaches `Presenter.Audio`/bridge, including the paused permit and an old-audio frame below its barrier; additionally verify no unintended slide advance (D-05). A fake cannot prove intelligible words, so retain the prompt assertion alongside audio delivery and a live run.

- **D-07 · should-fix · Same-slide `go_to_slide` skips the queued presenter command and confirmation precedence.** `src/PresenterAi.Application/Presenting/Tools/GoToSlideTool.cs:39-60`, `src/PresenterAi.Application/Presenting/Presenter.cs:1403-1427,1780-1808`. While awaiting an end confirmation, backend calls `go_to_slide` for the slide already displayed. `GoToSlideTool` returns "already on slide" from its snapshot without calling `IPresenter.GotoAsync`; the confirmation is not cancelled, even though plan §3.7 says Goto (including tool/voice/button) cancels it. A later `confirmed:true` can end the talk after the user intended navigation. Route same-slide tool navigation through the public command, or explicitly cancel the phase on the loop; test the same target while end-pending. Likewise `ResumePresentationTool.cs:28-39` short-circuits an already-presenting resume during check-in without clearing that phase; do not skip command-side phase effects.

- **D-08 · should-fix · The 4 KiB tool-result cap is not enforced on heavily escapable messages.** `src/PresenterAi.Application/Tools/ToolResult.cs:21-67`. For `ToolResult.Success(new string('\\', 5000))`, the final fallback truncates *unescaped* UTF-8 bytes to ~4,032 and then JSON-serializes it: each backslash doubles, so the returned output exceeds 4 KiB. A cut through multibyte UTF-8 can also introduce replacement characters. The strict output budget from plan §3.1 fails when an external tool returns escaped/unicode text. Size the **serialized** JSON after truncation (e.g. binary search over Unicode scalar boundaries) and assert final UTF-8 length ≤ 4096 in tests with backslashes/quotes/non-ASCII.

- **D-09 · should-fix · Concurrent tool registration and session snapshot are not synchronized.** `src/PresenterAi.Application/Tools/ToolRegistry.cs:20-29,72-87`, `src/PresenterAi.Application/Presenting/Presenter.cs:132-133,460-465`. Plan §3.1 permits a registry change to appear at the *next* Start; `ToolRegistry` is exposed publicly and registered singleton. If registration on another thread races `GetAllTools()` at Start, enumerating the `Dictionary` can throw and `StartAsync` fails instead of producing one consistent catalogue. Lock or use an immutable/copy-on-write registry for register/enumerate, and test concurrent registration/start snapshots. This was present before 9f25d91 but missed in round 1.

- **C-01 · should-fix · Revised guide states the wrong default managed tool list.** `docs/guides/002-audience-questions.md:105-110` says `"tools: [pinned tools, find_tools, call_tool]"`. The normal six built-ins with `Tools:MaxInlineTools=16` use the **all-inline** branch (`ToolSessionCatalogue.cs:26-29`) and include no `find_tools`/`call_tool`; those exist only above the threshold (`:30-46`). A reader troubleshooting missing meta-tools in a default session will assume startup is broken. Describe both threshold branches, or show the list as conditional. The guide's `:178` claim that client delegation is answered "while paused" is likewise unsupported: `Presenter.cs:1014-1030` returns before `AppendInstructions` unless state is Presenting. Qualify the claim or implement paused client-delegation replies.

- **Round-1 row 4, rejected half:** no renewed finding about transcript-before-output *for the browser's own loudspeaker echo*.
