## Findings

### Blockers

1. **D · blocker — Tool timeout is only cooperative, not a five-second deadline.** `src/PresenterAi.Application/Presenting/Presenter.cs:1134-1194` awaits `tool.InvokeAsync` with a token that cancels after five seconds but never bounds the await. An extension tool that ignores cancellation or hangs forever never posts `ToolInvocationCompleted`; its delegation cannot receive an output or pass the global barrier (`ToolRoundTracker.cs:146-163`). The existing `SlowTool` in `PresenterToolTests.cs:238-279` cooperates with cancellation, so it misses this case. Race invocation against a real timeout (`WaitAsync` or equivalent), post exactly one timeout result, observe late faults, and invalidate/cancel the work on End/restart/disposal.

2. **D · blocker — Navigation leaves abandoned calls in the active tool barrier.** `src/PresenterAi.Application/Presenting/Presenter.cs:1198-1219,1399-1403`, `src/PresenterAi.Application/Presenting/ToolRoundTracker.cs:146-163`. Start a slow call `c1`, press Next, then complete `c1`: its result is correctly dropped for the changed generation, but its tracker entry remains unsubmitted. Even after `response.completed`, `ShouldSendContinueResponses()` is permanently false. The same happens if two navigation calls are issued in one round and the second overwrites `_navigatingCallId`: only one can return an output. The navigation-staleness test at `PresenterToolTests.cs:281-309` asserts only that no stale output is sent, never that the tracker/barrier can recover. Explicitly close/invalidate affected rounds on navigation (and define how to unblock/abort the upstream response), or track *each* navigation call separately and provide a safe result for each required output; test subsequent calls and barrier progress.

3. **D · blocker — Backend pending does not actually protect the question hold from the 15-second escape.** `src/PresenterAi.Application/Presenting/Presenter.cs:1590-1597,1617-1627` calls `ResumeAfterQuestion` at 15 seconds even when `_toolRoundTracker.HasPendingBackendDelegation` is true. A tool taking several seconds followed by a slow backend can run past 15 seconds: the slide receives a resume bridge and advances before the delegated answer; when it finally completes, `FinishBackendDelegation` re-arms a question timer without reopening the hold (`Presenter.cs:1064-1079`). Keep the hold while any delegation is open, and start the unanswered escape only after the backend fails/completes; exercise a pending tool/backend across 15 seconds. The current hold oracle `PresenterToolTests.cs:410-445` waits only 3 seconds.

4. **D · blocker — Echo eligibility checks only output already received, not the whole utterance, and stale output history crosses runs.** `src/PresenterAi.Application/Presenting/Presenter.cs:750-775,791-806,453-455,654-663`. If the microphone transcript for an echoed "yes" arrives before the matching voiced output frame, the 700 ms gap can expire before audio arrives: `_voicedIntervals` has no overlap and the end confirmation is accepted. Conversely `_lastVoicedAt` is not reset on Start/End while the intervals are: immediately after a restart, a timestamp-less legitimate "continue" within 300 ms of the last run can be rejected. Delay non-Pause eligibility until output overlapping the full interval is known (or apply a bounded conservative output watermark), and reset both timestamp-based and wall-clock speech history on run/session transitions. Test transcript-before-output and a quick restart; current voice tests deliver model audio first (`PresenterVoiceCommandTests.cs:79-100,164-193`).

5. **D · blocker — Out-of-range local navigation is silent, contrary to AC3.** `src/PresenterAi.Application/Presenting/Presenter.cs:834-841,1380-1391,791-825`. In a two-slide client-mode deck say "go to slide 40": matcher recognizes it, `GotoCore` returns false and logs a warning, then `CompleteUtterance` treats it as an ordinary question. There is no explicit spoken range reply (and in client mode the prompt only explains unsupported *topic* navigation); the model need not speak the valid range. On a recognized invalid local target, append an explicit spoken range response without navigating or issuing the question-resume bridge, with a paused output permit if needed. Test audible output in both delegation modes.

### Should-fix

6. **D · should-fix — Tool calls arriving during End are accepted on the still-current session.** `src/PresenterAi.Application/Presenting/Presenter.cs:1100-1121,1198-1230,1484-1515`. `EndAsyncCore` clears the tracker but leaves `_session` assigned while `CloseAsync` awaits upstream closure. A late `function_call` in that window recreates a tracker delegation and can invoke a tool or submit output while Ending. Reject calls/completions unless state is live and tracker delegation belongs to this run, and invalidate on entering Ending. Include a controlled close-delay test.

7. **D · should-fix — A tool result can be marked submitted and a barrier continued even if transport refuses the output.** `src/PresenterAi.Application/Presenting/Presenter.cs:1218-1230`; `src/PresenterAi.Infrastructure/Live/LiveSession.cs:180-209`. `MarkCallSubmitted` precedes `SubmitToolOutput` and neither its boolean nor `ContinueResponses()`'s boolean is checked. If the upstream closes between the checks or the enqueue fails, the tracker advances as though an output was sent; exactly-once *submission* and one valid barrier no longer hold. Check both results and handle session failure/teardown, keeping state transitions consistent with the writer queue.

8. **D · should-fix — Check-in "no" drops the question hold instead of keeping it.** Plan §3.7 requires "No → stay on the slide, hold kept for the next question". `src/PresenterAi.Application/Presenting/Presenter.cs:849-853,810-815` clears the silence timer, but `CompleteUtterance` immediately calls `ClearQuestionHold()` for any successful command. Subsequent voiced audio can re-arm the ordinary slide/part timer (`Presenter.cs:705-736`) and advance without a new question. Preserve the hold for check-in No, while still suppressing the resume bridge, and test a subsequent output plus silence.

9. **D · should-fix — Utterance duration cap is evaluated only when a delta arrives.** `src/PresenterAi.Application/Presenting/Presenter.cs:750-765,791-803`. A short first delta followed by a 5.9 s gap-free series ending at 5.9 s, and another 700 ms silence, is correctly bounded; but a single delta with `start_ms=0,end_ms=7000` is accepted as a command immediately after the 700 ms timer, because elapsed wall-clock at append is ~0 and no duration is checked at completion. Check both accumulated transcript timestamps and elapsed wall-clock on completion; test a single >6 s delta.

10. **D · should-fix — The public catalogue is not an immutable snapshot.** `src/PresenterAi.Application/Tools/ToolSessionCatalogue.cs:17-24,51-78`; `src/PresenterAi.Application/Presenting/Presenter.cs:132-134`. Dictionaries snapshot *ITool references*, and `GetInlineToolDefinitions()` returns the actual mutable `JsonObject`s; an API consumer can alter a tool's mutable `Parameters` or the exported definition mid-run. Then `find_tools`/`call_tool` validates against different schema than `session.start` advertised, and the serialized 32 KiB budget can be exceeded after construction. Deep-clone definitions/schemas, return defensive copies and avoid exposing mutable tracker internals publicly; test mutation after snapshot, not only registry additions.

11. **B · should-fix — 100-tool budget oracle measures the wrong payload.** `tests/PresenterAi.Application.Tests/Tools/ToolSessionCatalogueTests.cs:139-185` measures only the JSON array returned by `GetInlineToolDefinitions()`, despite plan §5 Task 1 requiring measurement of the *real `session.start` payload*. A wrong implementation adding 40 KiB of `session.start` metadata or duplicating definitions elsewhere passes this test. Capture the actual `session.start` from `FakeLiveServer` with 100 registered tools, assert selected names AND byte budget in the actual envelope (specify whether the 32 KiB applies to the list or full start frame).

12. **C · should-fix — Audience guide's protocol flow is stale.** `docs/guides/002-audience-questions.md:104-127` claims `responses` contains only `{model,instructions,reasoning,service_tier,text}`, describes `response.completed` as answer-ready, and says the follow-up timer fires through `OnSilence`/`HoldBlocksProgress`. Code includes `tools`, `tool_choice`, `parallel_tool_calls` (`src/PresenterAi.Infrastructure/Live/LiveSession.cs:683-693`); a tool-round completion is *not* answer-ready (`Presenter.cs:1039-1060`); check-in is driven by `InteractionElapsed` (`Presenter.cs:910-939`). An operator following the guide will misdiagnose a tool round as a finished answer. Update diagrams, timer table and log interpretation to match the tracker/phases.

13. **C · should-fix — "nothing mutates presenter state off the single-reader loop" is not literally true.** `src/PresenterAi.Application/Presenting/Presenter.cs:265-276,1782-1784` lets `ObserveBackground` call `LogMessage` directly from a continuation (on a thread-pool scheduler); a `Log` subscriber is therefore invoked off-loop and can enqueue bridge frames out of order. The code comment at `Presenter.cs:20-24` says "all output events are owned by its single channel consumer." Route background failure notification through the event channel, or qualify the guarantee and ensure ordering.

14. **D · should-fix — Transcript text is emitted into an info log on rejected commands.** `src/PresenterAi.Application/Presenting/Presenter.cs:804-807` logs the entire `phrase.Trim()` even though voice command detection runs on audience transcripts; `src/PresenterAi.Infrastructure/Live/LiveSession.cs:455-462,503-507` also logs raw upstream JSON (including new function arguments) when event logging is enabled. Example: an audience says a private sentence that happens to match "yes" during model speech, and it is persisted in the host log. Log intent/rejection only and redact transcripts and tool argument bodies from event logging (retain names/ids); verify log privacy with both logging modes.

15. **D · should-fix — Invalid `confirmed:true` result is a success-shaped confirmation message.** `src/PresenterAi.Application/Presenting/Tools/EndPresentationTool.cs:42-52`; `Presenter.cs:971-980`. A model calls `end_presentation{confirmed:true}` before `AwaitingEndAnswer`: presenter starts asking for confirmation, but tool returns `ok:true` even though there has been no confirmation. The backend may then tell the audience the talk ended. Return `ok:false`/explicit pending status for premature confirmation and reserve success/"ended" for a real end; test model call before the question is voiced.

## Wiring, precedence and oracle notes

- Six presenter tools invoke `IPresenter` methods, not private cores (`src/PresenterAi.Application/Presenting/Tools/*.cs`); `ToolCallRequested` → `Presenter.WireSession` → tracker → catalogue → public methods (`Presenter.cs:553-564,1100-1231`). `Flush` → bridge frame (`PresenterBridge.cs:57-62`) → client event (`bridgeClient.ts:222-226`) → playback flush (`Present.tsx:139-142`). The only new browser event is `flush`; tool frames stay upstream. State changes in cores and phase timers happen on the reader except background Log notification #13; `Task.Run` carries AsyncLocal only to identify the originating navigation command.
- Input gates: browser admits presenting/paused (`bridgeClient.ts:187-193`), presenter admits presenting/paused if not muted (`Presenter.cs:1453-1476`), upstream mute/unmute is issued in both states (`Presenter.cs:1453-1470`). Idle/ending drop mic input; paused output requires a permit and barrier (`Presenter.cs:632-651`); presenting output flows. Browser itself does not test `snapshot.muted` in `sendAudio`, but presenter does; this is not an upstream leak. End-pending buttons/navigation go through `ProcessCommandAsync`/`LeavePauseForNavigation`; End bypasses confirmation. The stale-result and pending-round exceptions are #2/#6.
- `PresenterVoiceCommandTests` misses transcript-before-audio and long single delta (#4/#9); `PresenterToolTests` misses noncooperative timeout, barrier recovery and 15-second pending backend (#1-#3). No standalone tracker test was found; tracker is exercised through presenter tests (`PresenterToolTests.cs:158-237`). `ToolSessionCatalogueTests` has the wrong budget subject (#11), while its registry-addition snapshot oracle is meaningful but does not cover mutation (#10). `BridgeTests.cs:34-36` checks that *some* flush arrives after pause; a wrong implementation sending flush on every state event would pass—assert exactly one per pause and none for resume/idle. `VoiceCommandMatcherTests.cs:86-95` does reject extra words but cannot catch echo ordering (matcher has no timing). `bridgeClient.spec.ts:225-253` checks paused/presenting/idle and event forwarding; a wrong client emitting flush twice or accepting mic while muted still passes (muted suppression is intentionally at presenter). `Present.spec.tsx:145-158` proves playback flush when audio exists but not that stale queued audio is dropped before any delayed server audio; add an ordering assertion with enqueue/flush.
