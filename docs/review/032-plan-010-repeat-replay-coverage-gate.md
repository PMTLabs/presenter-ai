# 032 — Plan 010: gating the repeated-request replay on narration coverage (pi, gpt-6-sol medium)

**Date:** 2026-09-25. **Trigger:** T13 row 5 on the 011 build with `889e61f`: the repeat got `already_done`, the model
stayed quiet and finished slide 3, and the unconditional replay then spoke the slide a second time. The first live run
(before `889e61f`) had the opposite outcome: the model spoke over the replay and the rest of slide 2 was lost.

## What was adopted, and where the implementation differs from the report
- Adopted the conservative P1 variant: a separate flag (`_repeatReplayDue`) that never cancels `_replayOnResume`; the
  decision is made at the resume (question resume and `ResumeCore`, via `TrainingOverridesResume`); unknown means replay;
  the transcript buffer is reset on every `PresentSlide`; the flag is cleared on navigation (`PresentSlide`), wrap-up,
  Start/End and reconnect; Unicode-aware tokens; the log carries the coverage, not the transcript.
- The criterion is stronger than the report's "last-part tail" worry: it is whole-slide coverage (at least 90 % of all
  the slide's words in order, across all parts joined) **and** the last six words contiguous, **and** all parts sent. A
  quoted sentence or a cut-off ending cannot pass; multi-part slides are covered by the whole-narration measure.
- Not adopted: requiring the match to precede the repeat. In the live run the slide was finished *after* the repeat,
  so that rule would keep the double replay. An answer cannot reach 90 % coverage of the whole slide.
- Ask exchange (plan 011): the flag is not set inside an exchange (its `ReplayDue` owns replays), and an open flag is
  settled at Ask start before `ReplayDue` takes over the pending replay.

# pi-rg-01 — repeated `revise_script` replay gate (review only)

## Verdict

**Recommend a conservative P1 variant, not P1 as stated.** Run 2 demonstrates that unconditional replay is wrong, but P2 cannot guarantee delivery after an interruption: the earlier run skipped the remainder of slide 2. Keep the structural replay fallback, and suppress **only the replay caused by this particular applied-edit repeat** when there is convincing evidence that the **entire final narration part** was voiced. Do not suppress a replay due to a newly applied edit, failed-edit release, or Ask exchange. Transcript coverage is evidence, not a completion event; log the decision and validate it on real runs before treating it as reliable. P3 remains the safe fallback when evidence is absent or ambiguous. The backend `already_done` rule reduces unsolicited speech but cannot guarantee silence (`src/PresenterAi.Application/Presenting/PromptBuilder.cs:216`; `docs/review/031-plan-010-repeated-revise-script-impact.md:207-223`).

### Blockers to P1 *as written*

1. **Last-eight-word overlap is not proof of finished narration.** An in-order subsequence of 6/8 can occur in a quoted edit, an answer, a repeated phrase earlier in the slide, or an unfinished sentence; “within the transcript's tail” needs a defined bounded window and an end anchor. Checking only the last part does not establish earlier parts were spoken. The presenter sends a part, rather than waiting for its completion (`src/PresenterAi.Application/Presenting/Presenter.cs:1011-1037,1990-2001,2702`); `session.output_transcript.delta` supplies deltas, not end-of-slide events (`src/PresenterAi.Infrastructure/Live/LiveSession.cs:552-558`). If a final part was sent prematurely or an answer quotes its end, a false positive **loses content**. For fewer than eight words, “at least six” cannot work at all. Vietnamese needs Unicode letters/marks and numbers, not an ASCII `[a-z0-9]` regex; don't split diacritics off base letters.
2. **The shared replay flag is not exclusively about duplicates.** Reconcile sets `_replayOnResume` when an edit applies while paused, and may carry a failed-edit lead (`src/PresenterAi.Application/Presenting/Presenter.Training.cs:553-574,634-651`). `PresentSlide` clears that flag (`src/PresenterAi.Application/Presenting/Presenter.cs:954-970`); Ask transfers it into `exchange.ReplayDue` (`src/PresenterAi.Application/Presenting/Presenter.Asking.cs:278-293`). A coverage check must never cancel either obligation. A separate duplicate-only flag must be consumed/invalidated independently.
3. **Don't route Ask through the normal question gate.** Ask start clears `_approvedTools`, so only a confirmation established *within* that exchange can repeat there (`src/PresenterAi.Application/Presenting/Presenter.Asking.cs:277-306`). A reconciliation during Ask sets `ReplayDue`; `ResumeAfterExchange` handles it before ordinary question resume (`src/PresenterAi.Application/Presenting/Presenter.Training.cs:545-551`; `src/PresenterAi.Application/Presenting/Presenter.Asking.cs:1140-1162`). An applied edit during Ask has not been replayed yet. Suppressing `ReplayDue` because an earlier transcript ends like the edited slide would skip the updated narration. Leave the existing Ask behavior intact; do not leak a duplicate-only flag into the post-Ask question path.

## Code-path assessment and implementation boundaries

- `OnTranscript` first verifies session identity, publishes the delta, then calls `RecordRecentTurn` (`src/PresenterAi.Application/Presenting/Presenter.cs:1142-1154`). Collect assistant-role deltas **there**, separately from `_recentTurns`: that reviser context is role-contiguous, limited to eight turns and 1,000 characters per turn, and also includes user speech (`src/PresenterAi.Application/Presenting/Presenter.Training.cs:703-720`). It is not a slide coverage buffer. Bound the new transcript storage, preserve token boundaries across deltas, and keep a slide/presentation generation with the captured narration snapshot. Output transcript can include answers and other speech; audio forwarding/holds can reject output while transcript still arrives (`src/PresenterAi.Application/Presenting/Presenter.cs:1040-1070,1142-1152`). Therefore a transcript match alone does **not** prove the audience heard it. Require the appropriate presentation state/forwarded audio evidence if available; otherwise choose replay. Delayed old-session events are rejected, but delayed same-session deltas following `PresentSlide` are not attributed to the instruction that produced them (`Presenter.cs:1142-1150`). Treat near-reset matches conservatively.
- Reset slide transcript **on every** `PresentSlide` (including replay, same-slide navigation, held/empty slide); `ReplayCurrentSlide` calls it (`src/PresenterAi.Application/Presenting/Presenter.Training.cs:613-628`; `src/PresenterAi.Application/Presenting/Presenter.cs:954-1009`). Clear duplicate-only replay on navigation, new `PresentSlide`, wrap-up, Start/End, and session replacement; avoid clearing a still-valid replay just because of pause. `StartWrapUp` does not call `PresentSlide` (`Presenter.cs:2055-2073`), so clear explicitly there. Start and close already reset other training fields (`Presenter.Training.cs:122-139,200-229`). Navigation includes manual Next on the last slide, which starts wrap-up (`Presenter.cs:2080-2094`); successful navigation also clears approvals (`Presenter.cs:2131-2138`). Auto-advance calls `PresentSlide` and must invalidate the old slide's flag (`Presenter.cs:1980-2008`). On reconnect, old transcript and repeat flags must not be mistaken for output in the new session; `ResumeAfterReconnectAsync` checks `NarrationHeld || _replayOnResume` before calling `ResumeCore` and otherwise re-presents the slide (`Presenter.cs:2200-2233`). In particular, do not replace a due paused-edit replay with only `ResumeInstruction`; decide whether to replay or deliberately re-present after reconnect (`Presenter.cs:2253-2285`). Suspending a session without closing the talk is different from `OnClosed` (`Presenter.cs:2154-2168,2398-2433`).
- `TextChunker` collapses whitespace, splits at `[.!?]`, and splits long sentences by length (`src/PresenterAi.Application/Scripts/TextChunker.cs:7-78`). Match against the *actual last chunk* `_parts[^1]`, not original raw narration, and require `_partsSent == _parts.Count` **and** evidence of every earlier part, or keep replay. `PartsPending` means *not yet sent*, not *not yet spoken* (`Presenter.cs:1011-1037,1973-2001`). For one-part slides it is false immediately on send. A short final chunk needs a stricter separate policy (e.g. exact normalized full-chunk match plus prior-part evidence), not a six-word threshold. An empty narration has no end match: do not infer completion. An edited version arriving during observation must invalidate coverage for the old text (`Presenter.Training.cs:480-510`).
- At the cached approval branch `AnswerRepeatedScriptEdit` is called only when the approval key matches inside 60 s (`Presenter.cs:1683-1697`). It returns false for unsettled edits, leaving the old `running`/cached result; failed edits yield failure, never a duplicate replay; applied edits targeted elsewhere return `already_done` without replay (`Presenter.Training.cs:392-414`). Target slides are in the approval key (`Presenter.cs:1686-1692`). Keep these semantics. A pending confirmation has no approved key. Only create the duplicate replay obligation when a current-slide *applied* repeat actually interrupts a current slide and an ordinary question hold owns its resume; otherwise avoid leaving a latent flag. No broad changes to other confirmed tools.
- At question release, `ResumeAfterQuestion` clears the hold, checks `NarrationHeld`, then currently uses `_replayOnResume`/`TrainingOverridesResume` or appends `ResumeAfterQuestionInstruction` (`Presenter.cs:2505-2525`). Consume a duplicate-only flag **there before the ordinary path**, with slide/generation checks; preserve the shared replay if it was set independently. On proven completion, use normal question resume (transition + wait for voiced output/fallback), *not immediate advance* (`Presenter.cs:2513-2556`), and only if this was the sole replay reason. On incomplete/unknown coverage, replay once. The no-answer 15 s release also calls this method (`Presenter.cs:2475-2485`), so unknown transcript must replay. `HoldBlocksProgress` prevents advancement while held (`Presenter.cs:2486-2503`).
- Manual Pause can close timers and hold, but not necessarily close the question; `ResumeCore` clears the question hold and checks `TrainingOverridesResume` (`Presenter.cs:2139-2160,2235-2285`). Specify and test ownership across Pause/Resume: either retain and consume duplicate obligation on `ResumeCore`, or deliberately clear it and re-present the slide. Never discard it merely because `ResumeAfterQuestion` was bypassed; never discard an unrelated `_replayOnResume`. For Ask, decide before transfer and let `ReplayDue` continue to own reconciled-edit replays. Last-slide successful completion should resume the ordinary silence → `StartWrapUp` path, not trigger immediate End (`Presenter.cs:1980-2009,2055-2073`).

## Coverage criterion

The prompts request full, ordered, *minimally rephrased* narration (`src/PresenterAi.Application/Presenting/PromptBuilder.cs:42-49,118-143`), so verbatim tail matching is plausible for run 2, but not guaranteed: model paraphrases, transcript errors, punctuation, language-specific tokenization and reordered output produce false negatives. Those cause duplicates, which are preferable to false positives. There is **no reliable completion signal in current code**: audio activity, `_heardOutput`, `_partsSent`, `PartsPending`, silence timers, and `question: answered` cannot establish narration coverage (`Presenter.cs:1085-1140,1973-2009`).

A safer first version: only classify finished if all chunks have been sent, assistant-output evidence **since the latest slide presentation** contains a contiguous normalized end-of-last-part phrase (prefer a sufficiently distinctive longer suffix, exact ordered words), ending near the end of the relevant transcript; validate preceding chunk coverage or conservatively decline classification on multi-part slides. Restrict output to the period of actual forwarded narration if attribution is possible, not merely the answer to the repeat; never use a match found *solely after the repeat/tool answer* as proof. For short/repetitive tails and missing/truncated transcripts, classify **unknown → replay**. Tokenize Unicode letters/combining marks/digits (`\p{L}\p{M}\p{N}` or Rune categories), preserving Vietnamese marks; normalize consistently, but do not strip accented letters into unrelated ASCII words. Prefer a stronger attribution signal if upstream later supplies response/instruction IDs plus completed playback; neither is provided here (`LiveSession.cs:552-558`). Report matched length, chunk index and decision **without logging transcript text**. Even this is a heuristic: confirm by live run with usage seconds, especially an interruption after a fully spoken last sentence vs one before it.
